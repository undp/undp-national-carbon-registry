# 登记系统与交易系统补齐参考

本文档把现有 dashboard、两段交易系统录屏、官方规则/手册和登记系统前端工作流线索对齐，作为后续反推业务系统原型的参考。

## 资料结论

当前证据支持把系统拆成两个业务上下文：

- 登记系统：负责项目、减排量、持有、变更、转移、注销等资产权属事实。
- 交易系统：负责行情、委托、摘牌/成交、资金、清结算服务。

二者不是简单的两个无关系统。管理办法明确要求交易主体同时在注册登记系统和交易系统开设账户；交易成交结果由交易机构提供，注册登记机构据此在登记系统变更核证自愿减排量的持有数量和持有状态。因此原型可以是一个后端、两个领域模块，但数据模型必须保留“交易成交 -> 清结算 -> 登记持仓变更”的边界。

## 可确认业务子系统

| 子系统 | 证据来源 | 原型范围 |
| --- | --- | --- |
| 主体与账户 | `manuals/2023-registry-system-enterprise-account-opening-guide.pdf`、交易客户端手册 | 企业基础信息、法定代表人、联系人、登记系统代表、交易系统账户代表、联合开户/独立开户、开户进度 |
| 项目登记 | 管理办法、审定与核查实施规则、登记系统工作流 `ccerRegisterApply`/`ccerRegisterConfirm` | 项目业主、项目设计文件、公示、审定报告、登记申请、受理/审查/确认 |
| 项目注销 | 管理办法、登记系统工作流 `projectLogoutManage` | 项目业主自愿项目注销、机构调查核实注销、注销后不得再次申请登记 |
| 减排量登记/签发 | 管理办法、审定与核查实施规则、登记系统工作流 `ccerIssuedConfirm` | 监测、减排量核算报告、公示、核查报告、减排量登记申请、签发确认 |
| 持有与转移 | 管理办法、登记规则网页镜像、登记系统工作流 `ccerTransferConfirm` | 登记账户持有量、持有状态、转移申请/确认、跨系统成交后的持仓变更 |
| 交易 | 交易客户端手册、交易与结算规则、两段录屏 | 标的物、行情、盘口、挂牌买入、挂牌卖出、摘牌、撤单、成交查询 |
| 资金与结算 | 交易客户端手册、交易与结算规则 | 银行账户绑定、入金、出金、缴费、成交金额、手续费、结算结果 |
| 抵消及注销 | 管理办法、登记系统工作流 `ccerOffsetConfirm`/`ccerOffsetAudit` | 用于配额清缴、大型活动碳中和、企业排放抵消、公益自愿注销；注销发生在登记系统 |
| Dashboard 投影 | 本仓库 regional dashboard | 项目数、签发量、成交量、成交金额、注销量、地市余额、地市评分 |

## 核心业务实体

| 实体 | 所属上下文 | 说明 |
| --- | --- | --- |
| `Organization` | 共享主体 | 法人或其他组织；可同时是项目业主、交易主体、履约主体 |
| `RegistryAccount` | 登记系统 | 记录减排量登记、持有、变更、转移、注销 |
| `TradingAccount` | 交易系统 | 参与交易系统委托、成交、资金管理 |
| `Operator` / `Representative` | 共享主体 | 登记系统发起代表、确认代表、交易账户代表、操作员权限 |
| `Project` | 登记系统 | 自愿减排项目；含业主、地区、方法学、项目设计文件、状态 |
| `ValidationReport` | 登记系统 | 项目审定报告，支撑项目登记 |
| `MonitoringReport` | 登记系统 | 项目实施与减排量核算材料 |
| `VerificationReport` | 登记系统 | 减排量核查报告，支撑减排量登记 |
| `CreditIssuance` | 登记系统 | 减排量登记/签发事件，形成可持有资产 |
| `CreditHolding` | 登记系统 | 登记账户下的可用、冻结、已注销等持仓状态 |
| `TransferApplication` | 登记系统 | 持有量转移申请/确认 |
| `Instrument` | 交易系统 | 交易标的物，可映射到 CCER 品类/批次/年份等 |
| `Order` | 交易系统 | 挂牌买入/卖出委托 |
| `TradeDeal` | 交易系统 | 成交结果，是 dashboard 成交量/买入/卖出的事实源 |
| `ClearingResult` | 交易系统/接口 | 成交后的清结算结果，触发登记系统持仓变更 |
| `BankAccount` / `FundFlow` | 交易系统 | 银行账户绑定、入金、出金、手续费缴纳 |
| `Retirement` / `Cancellation` | 登记系统 | 抵消及注销、公益自愿注销、强制注销 |

## 端到端闭环

推荐的业务闭环为：

1. 主体开户：企业在登记系统独立开户，或登记系统与交易系统联合开户。
2. 项目登记：项目业主提交项目设计文件、公示、审定报告，登记机构受理并登记。
3. 减排量登记/签发：项目业主提交监测和核算材料，经核查后申请减排量登记，形成登记账户持仓。
4. 供给侧卖出：持有 CCER 的主体在交易系统挂牌卖出，卖出前需要足额持仓。
5. 履约侧买入：买方在交易系统挂牌买入或摘牌买入，买入前需要足额资金。
6. 成交与清结算：交易系统生成成交结果和清结算结果。
7. 登记持仓变更：注册登记机构根据成交结果变更买卖双方持有数量和状态。
8. 抵消及注销：履约主体或自愿注销主体在登记系统提交抵消及注销申请，审批/确认后扣减持仓。
9. Dashboard 汇总：按登记系统和交易系统全量事实表聚合项目、签发、成交、注销、余额和评分。

## Dashboard 指标映射

| Dashboard 指标 | 事实源 | 计算建议 |
| --- | --- | --- |
| 项目数 | `Project` | 全量已登记项目数；最近项目列表只展示 `recentProjects` |
| 签发量 | `CreditIssuance` | 全量已登记/签发减排量；按项目所在地归入供给地 |
| 成交量 | `TradeDeal` | 全量成交结果，不用最近成交列表反推 |
| 成交金额 | `TradeDeal` | `sum(quantity * price)` 或结算结果金额 |
| 买入量 | `TradeDeal` | 按买方主体所在地/履约地归集 |
| 卖出量 | `TradeDeal` | 按卖方主体所在地/供给地归集 |
| 注销量 | `Retirement` / `Cancellation` | 按注销主体所在地/用途地归集；项目注销和减排量注销要分开 |
| 可用余额 | `CreditHolding` 或投影表 | `本地签发 + 买入 - 卖出 - 注销`；真实系统应以登记持仓为准 |
| 地市评分 | 聚合投影 | 围绕供给能力、履约压力、闭环质量计算 |

## 与当前原型的落地约束

- `recentProjectRegistrations`、`recentTrades` 只能驱动列表、轮播和最近动态，不能参与地图评分和全量指标。
- 郑州示例如果要讲“签发 1,500、买入 900、注销 300、余额 2,100、评分约 87”，后端真实种子和前端 demo 必须同一套故事。
- 注销如果解释为履约闭环，注销主体应是买方/履约主体；项目业主注销应单独命名为项目注销或自愿注销，不能混成履约注销。
- 两段录屏能支撑交易客户端原型，包括行情、盘口、挂牌、摘牌、成交和资金查询；不能支撑项目登记、签发、核证、抵消及注销的完整表单。
- 国际登记簿资料只用于补齐通用抽象，如账户、项目、批次、转让、注销、公开查询；国内规则存在明确要求时，以国内规则为准。

1. 补齐登记系统完整操作手册或更多录屏，抽取项目登记、核证登记、签发、转移、抵消及注销的表单字段和状态机。
2. 定位项目设计与实施指南正文 PDF，补齐项目层面的材料结构、方法学引用和实施要求。
3. 将 `TradeDeal -> ClearingResult -> RegistryHoldingChange` 做成接口契约，避免交易系统和登记系统各自改余额。
4. 为 dashboard 加一致性测试：全量签发等于地市签发合计；全量成交等于买卖两侧合计；注销不得超过可用持仓；最近列表不得参与全量评分。
5. 把账号分类从“重点排放单位”改为更中性的“交易主体/项目业主/审定与核查机构/主管机构”，除非后续资料能证明真实重点排放单位口径。
