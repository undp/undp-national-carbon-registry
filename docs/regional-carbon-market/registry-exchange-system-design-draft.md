# 登记系统与交易系统设计草稿

## 背景

本文沉淀基于 `v1.mp4`、`v2.mp4` 结构化抽取后的系统边界判断，用于后续从 dashboard 反推业务系统、设计交易系统原型和登记系统接口。

相关来源：

- `notes/video-analysis/v1-structured-extraction.md`
- `notes/video-analysis/v2-structured-extraction.md`
- `docs/regional-carbon-market/terminology-guardrails.md`
- `docs/regional-carbon-market/demo-flow.md`

当前结论：

- `v1.mp4` 和 `v2.mp4` 主要展示的是交易系统/交易终端。
- 两段视频没有直接展示项目注册、项目登记、核证、签发、履约注销等登记系统流程。
- `v2.mp4` 明确展示了 `登记系统->交易系统（转入）` 和 `交易系统->登记系统（转出）`，说明交易系统不是资产源头，而是交易场所和交易子账本。

## 系统边界判断

业务上应视为两个系统、两个账本：

```text
登记系统：
项目登记、资产签发、权属登记、余额总账、转入转出受理、注销/履约、监管审计

交易系统：
行情、标的物、买入申报、卖出申报、撤单、撮合/成交、资金、交易持仓、冻结、日终报表
```

工程原型阶段不建议直接拆成两个独立服务。建议先做成：

```text
一个后端
一个数据库
两个业务上下文
两套账本表
通过 TransferApplication 衔接
```

这样可以保留真实业务边界，同时降低早期分布式一致性成本。

## 两段视频能确认的交易系统能力

两段视频能较可靠支持交易系统原型的以下范围：

- 交易账户/操作员登录态
- 交易标的物，如 `CEA`、`CEA21`、`CEA22`、`CEA23`、`CEA24`、`CEA25`
- 行情、分时、K 线、分笔、F10 信息
- 买入申报
- 卖出申报
- 撤销申报
- 挂单交易
- 大宗协议
- 单向竞价
- 当日委托查询
- 当日成交查询
- 历史委托查询
- 历史成交查询
- 资金账户查询、可用资金、冻结资金
- 配额转入/转出
- 配额持仓/可转持仓查询
- 日终报表
- 用户信息和密码管理

视频没有确认以下登记系统流程：

- 项目注册
- 项目登记审批
- 项目核证
- 信用/配额签发
- 项目业主端签发申请
- 主管机构审批
- 履约注销/抵销注销

这些能力需要来自其他输入，例如操作手册、PRD、登记系统录屏、历史系统归档、代码或访谈。

## 买入申报与 dashboard 买入量的关系

交易视频里的“买入”是交易过程动作：

```text
买入申报
  -> 委托挂单
  -> 资金冻结
  -> 撮合/成交
  -> 生成成交记录
  -> 买方获得交易系统持仓
```

dashboard 里的“买入量”应是成交结果口径：

```text
已成交买入量 = 成交记录里买方归属到某地市的实际成交数量
```

因此：

- 未成交买单不能进入 dashboard 买入量。
- 已撤单买单不能进入 dashboard 买入量。
- 部分成交买单只按实际成交数量进入买入量。
- 已成交买单按成交数量进入买方地市买入量。

dashboard 的成交量、买入量、卖出量应来自交易系统 `Deal` 或成交结果投影，而不是 `Order` 或买入申报表。

## 完整业务闭环

建议把完整业务闭环拆成登记系统、交易系统、履约/注销系统三段理解：

```text
登记系统：
项目登记 -> 核证 -> 签发 -> 登记系统可用余额

交易系统：
登记系统转入 -> 卖出申报 -> 买入申报 -> 撮合成交 -> 买方交易系统持仓

登记/履约系统：
交易系统转出 -> 买方登记系统余额 -> 履约注销 -> 注销量和期末余额
```

当前 dashboard 的指标来源应对应为：

| Dashboard 指标 | 推荐数据来源 | 不应直接来自 |
| --- | --- | --- |
| 项目数 | 登记系统项目登记/审批结果 | 交易系统标的物列表 |
| 签发量 | 登记系统签发账本 | 交易系统持仓 |
| 成交量 | 交易系统已成交记录 | 买入/卖出申报 |
| 买入量 | 交易系统已成交记录的买方归属 | 未成交买单 |
| 卖出量 | 交易系统已成交记录的卖方归属 | 未成交卖单 |
| 注销量 | 登记/履约系统已完成注销记录 | 交易系统成交 |
| 地市余额 | 登记账本 + 交易成交 + 注销投影 | 最近列表或前端 mock |

地市余额公式：

```text
期末可用余额 = 本地签发 + 买入 - 卖出 - 注销
```

## 登记系统与交易系统接口

视频里直接看到的跨系统接口是：

```text
登记系统 -> 交易系统：配额转入
交易系统 -> 登记系统：配额转出
```

但一个可迭代系统需要的边界接口不止这两个。

### 1. 主体映射

视频中可见以下身份层级不是同一个概念：

- 客户号
- 操作员号
- 交易账号
- 资金账号
- 配额登记账户

建议建模：

```text
Organization
RegistryAccount
TradingCustomer
TradingAccount
FundAccount
Operator
```

最小映射关系：

```text
Organization
  -> RegistryAccount
  -> TradingCustomer
  -> TradingAccount
  -> FundAccount
  -> Operator[]
```

主体映射是跨系统数据一致性的基础。没有这个映射，dashboard 无法可靠把交易系统成交归属到地市、企业、履约主体或项目业主。

### 2. 资产/标的映射

登记系统中的资产可能是年度配额、CCER、项目减排量或特定签发批次。交易系统中显示为可交易标的：

```text
CEA
CEA21
CEA22
CEA23
CEA24
CEA25
碳排放配额25
```

建议建模：

```text
RegistryAssetType / Vintage / CreditBatch
  <-> TradingInstrument
```

没有资产映射，登记系统里的签发、余额、注销和交易系统里的 `CEA25` 无法严谨对账。

### 3. 配额转入

业务含义：

```text
登记系统可用余额减少或冻结
交易系统可交易持仓增加
```

推荐状态机：

```text
Draft
  -> Submitted
  -> Accepted
  -> Completed
  -> Rejected
  -> Cancelled
```

核心规则：

- 转入数量不能超过登记系统可用余额。
- 转入申请处理中时，登记系统应冻结或预留对应数量。
- 转入完成后，交易系统增加可用持仓。
- 转入失败或撤销后，登记系统释放冻结余额。

### 4. 配额转出

业务含义：

```text
交易系统可用持仓减少
登记系统可用余额增加
```

核心规则：

- 转出数量不能超过交易系统可用持仓。
- 已被冻结在卖单里的持仓不能转出。
- 转出处理中时，交易系统应冻结或预留对应数量。
- 转出完成后，登记系统增加可用余额。

### 5. 余额查询与对账

不能只依赖转入/转出流水。至少需要对账以下余额：

```text
登记系统可用余额
登记系统冻结/转出中余额
交易系统总持仓
交易系统可用持仓
交易系统冻结持仓
在途划转量
已注销余额
```

推荐对账恒等式：

```text
资产总量 =
  登记系统可用余额
  + 登记系统冻结/转出中余额
  + 交易系统可用持仓
  + 交易系统冻结持仓
  + 交易系统转出中持仓
  + 已注销量
```

如果后续引入项目签发批次或序列号，应按资产批次维度做同样对账，不能只按总量对账。

### 6. 成交结果同步或查询

成交发生在交易系统内。登记系统是否每笔成交后同步改权属，取决于后续业务选择。

模式 A：交易系统内部持仓账本模式

```text
转入交易系统后，交易系统内部持仓就是交易账本
成交只改变交易系统持仓
转出时才回登记系统
```

优点：

- 更贴近视频中交易系统有独立持仓、冻结和转出查询的表现。
- 登记系统压力较小，不需要处理每笔交易的实时权属变更。

缺点：

- 必须有强对账机制，避免登记系统和交易系统长期不一致。
- dashboard 如需实时地市买卖量，需要消费交易系统成交投影。

模式 B：成交后登记系统同步变更权属

```text
每笔成交后，交易系统把成交结果同步给登记系统
登记系统同步变更权属
```

优点：

- 登记系统始终更接近全局权属事实。

缺点：

- 交易撮合和登记权属强耦合。
- 对性能、重试、幂等和分布式事务要求更高。

原型阶段建议采用模式 A：

```text
登记系统是资产总账
交易系统是交易子账
转入/转出是唯一资产跨账本通道
dashboard 从交易系统成交投影读取买入/卖出/成交量
```

## 数据一致性挑战与控制策略

挑战确实较大，但可以通过清晰账本分区控制。关键原则：

```text
不要让两个系统都随便改同一笔资产。
```

建议资产状态分区：

```text
登记系统可用余额
登记系统冻结/转出中余额
交易系统可用持仓
交易系统冻结持仓
交易系统已成交持仓
转出中持仓
已注销余额
```

关键动作的账本影响：

| 动作 | 登记系统影响 | 交易系统影响 |
| --- | --- | --- |
| 签发 | 增加登记系统可用余额 | 无 |
| 转入申请 | 冻结或预留登记可用余额 | 无或记录在途 |
| 转入完成 | 登记冻结量确认转出 | 增加交易可用持仓 |
| 卖出挂单 | 无 | 交易可用持仓减少，冻结持仓增加 |
| 撤销卖单 | 无 | 冻结持仓释放回可用持仓 |
| 买入挂单 | 无 | 买方可用资金减少，冻结资金增加 |
| 撤销买单 | 无 | 冻结资金释放回可用资金 |
| 成交 | 无，若采用模式 A | 买卖双方交易持仓/资金变更，生成 Deal |
| 转出申请 | 无或记录在途 | 交易可用持仓减少，转出中/冻结增加 |
| 转出完成 | 增加登记系统可用余额 | 交易转出中持仓确认减少 |
| 注销 | 登记余额减少，已注销量增加 | 无 |

必要工程约束：

- 所有跨账本动作必须有幂等键。
- 转入/转出必须有状态机，不能只做即时加减。
- 订单冻结、撤单释放、成交扣减必须在交易系统账本内原子完成。
- dashboard 只能消费已完成事实：完成签发、已成交交易、完成注销。
- 对账报表应成为 P0，不应等到后期再补。

## 原型实现建议

P0 目标：做出可解释的双账本交易闭环。

```text
企业拥有登记系统配额
-> 转入交易系统
-> 卖方卖出申报
-> 买方买入申报
-> 简单撮合或人工成交
-> 买方获得交易系统持仓
-> 买方转出回登记系统
-> 后续登记/履约系统注销
```

P0 实体：

```text
Organization
RegistryAccount
TradingCustomer
TradingAccount
FundAccount
Operator
TradingInstrument
RegistryAssetBalance
ExchangePosition
QuotaTransferApplication
Order
Deal
Retirement
ReconciliationSnapshot
```

P0 能力：

- 主体映射
- 资产标的映射
- 配额转入
- 配额转出
- 买入申报
- 卖出申报
- 撤单
- 简单成交
- 交易持仓查询
- 资金查询
- 当日委托/成交查询
- 登记余额/交易余额对账
- dashboard 成交投影

P1 能力：

- 历史委托/成交查询
- 日终报表
- 手续费字段和报表展示
- Excel/PDF 导出，可先做 mock 或 CSV
- 交易时间窗口校验
- 更完整的操作员权限

P2 能力：

- 大宗协议
- 单向竞价
- 交易意向信息发布平台
- 交易代码管理
- 合约信息查询
- 更接近生产的撮合规则

## 与当前 dashboard 的关系

当前 dashboard 应保持为投影视图，不应直接承担交易系统或登记系统源头职责。

推荐关系：

```text
登记系统 ledger
  -> project / issuance / retirement projections

交易系统 ledger
  -> deal / buyer-city / seller-city projections

dashboard
  -> reads regional dashboard projection
```

dashboard 指标口径：

- 项目和签发来自登记系统。
- 成交量、成交金额、买入量、卖出量来自交易系统已成交记录。
- 注销量来自登记/履约系统已完成注销记录。
- 地市余额由上述事实投影计算。
- 最近项目/最近成交只用于展示列表，不参与全量评分和地图聚合。

## 当前设计决策草案

1. 业务上视为两个系统：登记系统和交易系统。
2. 原型工程上先做单体应用里的两个业务上下文，不急于拆成两个服务。
3. 登记系统是资产总账；交易系统是交易子账。
4. 转入/转出是资产跨账本的唯一通道。
5. 交易系统内部成交不直接等同于登记系统注销。
6. dashboard 的买入/卖出/成交量只来自已成交 `Deal`，不来自申报 `Order`。
7. 注销发生在登记/履约侧，不在交易系统侧。
8. 数据一致性通过状态机、冻结/释放、幂等键和对账报表控制。
9. P0 原型必须包含主体映射、资产映射、转入/转出、订单、成交、持仓、资金和对账。

## 待确认问题

- 真实业务中成交后是否需要实时同步登记系统权属，还是只在转出时回登记系统。
- 资金系统是否在原型内真实建账，还是先只做可用/冻结字段和模拟结算。
- 撮合规则采用价格优先/时间优先，还是先做人工成交/简化撮合。
- 大宗协议和单向竞价是否进入第一版原型，还是作为 P2。
- 交易意向信息发布平台是否属于交易系统的一部分，还是独立门户。
- 履约注销是否只接受登记系统余额，是否明确禁止交易系统冻结资产直接注销。
